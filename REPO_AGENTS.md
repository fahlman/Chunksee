# Chunksee — Repository Instructions

Read with the shared `AGENTS.md`.

## Read, interpret, display

Ryan's rules, approved 2026-10-25:

- The code knows formats, not content. What exists (blocks, items, mobs, biomes, structures,
  versions) comes at runtime from the save, the installed Minecraft, the world's data packs
  and the language files.
- **WWMD — What Would Minecraft Do?** Do what Minecraft does, unless Ryan explicitly
  chooses otherwise.
- **Lists are for exceptions,** and exceptions are facts in the game's code that the data
  doesn't tell us. Each entry names its code source. Anything the data could supply is a defect.
- Code-only facts are regenerated by a tool at each release. They are never hand-typed and
  never kept per snapshot.
- **Show what we can.** Never hide saved data because it's unfamiliar. "Unknown" is only for
  the facts the data can't tell us.
- **No version numbers in code or UI text.** Data readers read any version whose files parse.
- **Be useful, not a pain.** Notices inform and never block.
- **No self-made maintenance.** A new Minecraft version should need no code change, or at
  most one tool run.

Chunksee presents facts supplied by ChunkseeKit and ChunkseeIndex. It does not decode game
files or keep another copy of game rules. Read the user's installed language files through Kit;
reading those files at runtime is not redistribution. Choose the user's language in the app,
with the game's English name and then a readable ID as fallbacks.

Existing implementation notes below describe the current code and its evidence; they are not
exceptions to these rules. The migration is coordinated in
[fahlman/ChunkseeKit#222](https://github.com/fahlman/ChunkseeKit/issues/222):
Kit's readers and generated code facts come first, then their published API is adopted here.
Names and naming exceptions are tracked on #438 and fahlman/ChunkseeKit#225; hidden saved facts
on #439 and fahlman/ChunkseeKit#229/#235; structure membership on #435 and
fahlman/ChunkseeKit#233; biome lists and colors on #436 and fahlman/ChunkseeKit#223; missing
pictures on #430/#433 and fahlman/ChunkseeKit#234/#236; and dynamic version notices on #434
and fahlman/ChunkseeKit#237. #431 retains the separately held snapshot preparation.
Map palettes, marker colors and SF Symbols are presentation choices; they must not decide what
exists or hide saved data. Existing cave-biome inference remains subject to Ryan's hold on
fahlman/ChunkseeKit#130.

## Project

Chunksee is a Mac app for viewing Minecraft: Java Edition worlds. Ryan approved it on 2026-10-09.
It was called MCWorld until 2026-10-10, when it and its engine (MCWorldKit, now ChunkseeKit) were
renamed (fahlman/Chunksee#75); earlier issues, PRs and commits use the old names.

- **First scope:** open a world and show a top-down view of it.
- **Later:** overlays for strongholds, villages and other structures. These aren't approved for
  work yet.
- **Dependency direction:** **Chunksee app → ChunkseeKit and ChunkseeIndex**. ChunkseeKit is the
  open-source engine that reads world files (fahlman/ChunkseeKit); the same package's ChunkseeIndex
  product owns shared aggregation. This app owns presentation. World-format rules belong in
  ChunkseeKit and are never re-implemented here.

## Approved decisions (Ryan, 2026-10-09)

- **Kind:** Mac app, developed as an Xcode project with a tracked `.xcodeproj`, SwiftUI
  interface.
- **Names:**
  - Product, repository, project and app target: `Chunksee`.
  - Unit test target: `ChunkseeTests`.
  - Bundle identifier: `com.fahlsing.Chunksee`.
- **Distribution:** local builds only. No release or distribution process is approved.
- **Signing owner:** Automatic signing with team `PUT2KYMV2W`, the same team as Euchre.
- **Sandbox:** App Sandbox and hardened runtime are on.
- **Entitlements:**
  - read-only access to files the user selects
  - app-scoped security-scoped bookmarks
  - outgoing network connections (`network.client`), used only to look up player names from Mojang
    when the user turns that on. Ryan approved this on 2026-10-10 (fahlman/Chunksee#11), off by
    default.
- **Data locations:**
  - The app reads only the world or saves folder the user picks with an Open panel, and the
    Minecraft folder chosen in Settings, for player names and installed item pictures. Worlds open only through File ▸ Open
    and Open Recent: File ▸ Open World (fahlman/Chunksee#108) was removed on Ryan's decision of
    2026-10-16 (fahlman/Chunksee#155).
  - Each dimension folder is a native read-only folder document (Ryan, 2026-10-13); the world
    folder is not a document but contains one for each dimension, and opening it opens them. In
    the older layout, the Overworld's `region` folder stands for it. macOS owns opening, Open
    Recent, window tabs (by the user's tab preference) and restoration. Dimensions of one world
    share its resources, which close with the last of them.
  - Opening a world folder keeps an app-scoped, read-only bookmark to it, because the sandbox
    grants a reopened or restored dimension document only its own folder; the world's
    `level.dat`, players and other dimensions are read through that bookmark.
  - It never writes to a world folder.
  - Saved places are annotations in the app's local preferences, keyed by the world bookmark's
    persistent identity, which survives folder moves. Navigation history and ruler endpoints
    belong to each dimension view, and are never stored in the world.
  - For player names, it reads `usercache.json` files under a Minecraft folder the user chooses in
    Settings (kept as a read-only bookmark). With online lookup on, it sends the UUIDs of players it
    can't name locally to `sessionserver.mojang.com` and keeps the returned names in its
    preferences.
  - Rendered tiles are kept in the app's Caches folder (about 1 GB at most).
    Tile and scan directories share a SHA-256 key of the full dimension ID; punctuation and
    nested paths must not alias another dimension. Older lossy dimension directories are not
    read or migrated because their contents may belong to a different dimension. Dimensions
    rebuild cached data once; existing world-level pruning reclaims old directories.

  - ChunkseeKit releases are annotated semver tags, and each tag needs Ryan's approval (see

  - `Package.resolved` is tracked, so every build resolves the same ChunkseeKit commit.

## Foundation structure

**Status:** a proposed target, coordinated on #469; it is not yet approved by Ryan. On
2026-10-27 Ryan asked to "unwind the code to its core" and build from the foundation instead of
layering features. He chose to restructure in place, app first, with ChunkseeKit changing only
where the app needs it. Until a rebuilding step below lands, the Modules notes describe today's
code. New work must fit this structure. A change that contradicts it needs Ryan's approval first.

### Layers

Dependencies point down. Each layer depends only on layers above it in this list, through their
public interfaces.

1. **Kit** (ChunkseeKit, ChunkseeIndex) reads saves and game files, owns every format rule and
   code-only game fact, and publishes a reader version for each kind of fact the app caches:
   terrain and surface, light, assets and region facts. The app never parses files.
2. **Game files** (`MinecraftResources` and the game-data and artwork libraries). One owner
   chooses the Minecraft folder and decides whether artwork is used. It always hands out game
   data: definitions, tags, model geometry, lighting rules and numeric biome data. It hands out
   the artwork capability (textures, colormaps and pictures) only while Use Game Artwork is on.
   Nothing else decides that policy (#466).
3. **World snapshot** (`WorldResources`). Each open world has one observable snapshot of what
   its windows show: definitions, lighting, night lighting, biome colors, players and version
   notices.
   - **One loader:** each part comes from one shared loader type (`RefreshLoader`, extended as
     needed), whose inputs are declared: the world's file changes plus the game-data and artwork
     identities.
   - **The loader owns staleness:** cancellation, "latest result wins", and a declared choice to
     keep or clear the last value when its inputs change.
   - **Views observe:** sessions and views read the snapshot; nothing pushes values into maps by
     hand.
4. **Map presentation** (`MapModel`). Each dimension's map has one presentation value: style,
   depth, block filter, lighting mode, shadows, biome blending and overlays.
   - **Chosen, not shown:** it records what the user chose and is saved as one per-dimension
     record. What can be shown now (Height only with a known height scale, for example) is
     derived from that choice plus availability and never written back.
   - **Styles declare what they use:** each style states which inputs it uses, such as material
     colors, lighting, shadows and close-up detail, so that rule is decided once.
   - **One drawing input:** one value derived from the presentation and the snapshot feeds the
     screen, Copy/Share and area export.
5. **Windows, menus and views** show the snapshot and the map presentation, and send user input
   to the owner of each setting. They never read files, build cache keys or decide rules.

### Caches

The caches are `TileCache`, `ScanCache` and the in-memory tiles. Each belongs to the code that
produces its output: region reads for scan facts, the renderer for tiles.

- **Typed keys:** each cache's owner builds its key from typed values of every input that changes
  its output, including Kit's reader versions, the game-data and artwork identities, and the
  presentation values the output depends on. Whole Kit values are used, never hand-copied fields.
- **The app's version covers only the app:** no hand-maintained counter stands in for a Kit or
  game-file input; the app's renderer version covers only its own drawing code.
- **A test enforces it:** a fixed-output test fails when output changes without a key change.
- **In-memory tiles carry their key,** and a tile whose key no longer matches is dropped. Today
  each `MapModel` setter decides for itself whether to reload. The audit found no bug there, but
  nothing enforces it.

### Rules for every change

- A setting, policy or mode has one owner, and its consumers receive the result, not a flag to
  check. A cross-cutting rule left to convention, a flag that defaults to the unsafe choice, or
  two handles told apart only by name is a required review finding.
- There is one copy of the latest-result rule, of each setting's default, and of each style's
  inputs.
- A step that moves a rule to its owner deletes the code it replaces in the same PR.

### Rebuilding steps

Each step is one PR that preserves behavior unless Ryan agreed otherwise. It is tested on the
real path and reviewed by the other agent. A paired copied-world timing comparison is required
when the renderer or region reads change. The findings are from the audit on #469.

1. **Game data and artwork:** #466 (approved).
2. **One world-snapshot loader.**
   - **Moves:** the six hand-written `WorldResources` refreshes and the coalescers in
     `SlimeChunks.swift` and `WorldIndexStore.swift` move onto the shared loader. Sessions observe
     instead of receiving pushes, and the duplicate library-identity checks go.
   - **Fixes:** saved lighting kept after a game-file reread (L2), statistics blanking on each
     save (L5), and maps receiving game files only through the biome-color read (L4).
3. **Cache identity.**
   - **Kit side:** Kit publishes the reader versions above.
   - **App side:** tile, Dark Spots and biome-color keys use typed whole values.
   - **Fixes:** #471 and C1–C4.
4. **Map presentation value.**
   - **Moves:** chosen versus effective settings, one saved record, one drawing input, and
     style inputs declared once.
   - **Fixes:** #470 and M2–M4.
5. **One notification path.** `MinecraftResources` publishes through Observation only (L3). This
   comes once steps 2 and 4 have removed the hand-written pushes.

Step 2 comes before 3 and 4 because the loader's declared inputs are what the cache keys and the
presentation build on.

**Pause:** feature work stays paused until these steps land, including #472 and
fahlman/ChunkseeKit#232 item 2. The Phase 0 PRs listed on #469 land first.

### Already sound

These parts keep their current design; steps reuse them rather than replace them.

- **Lifetimes:** `BackgroundWork` scopes own task lifetime, cancellation and draining.
- **Map rendering:** `MapModel`'s job and revision checks, and the single
  `RegionTileRenderer.scan` that tiles, hover, copied coordinates, portals, close-ups and export
  share.
- **Map items:** the shared `MapScene` for drawing, picking, accessibility and export.
- **File identity:** stamps and ScanCache fingerprints.
- **Block filter keys:** derived from the resolved IDs.
- **App-wide settings:** each already has one owner.

## Modules

VisibilityCommand owns the shared Show/Hide label, binding and action. Compact eye buttons show
the current state; context-menu symbols show the action (crossed eye for Hide, open eye for Show).

WorldCommands routes native commands through the focused document. Edit > Find keeps Find and
Save Search together; Shift-Command-F saves a nonempty, unsaved query through SearchModel. View's
Command-9 Fit World uses MapNavigation's existing fit/availability calculation. World Info and
Storage share one native toggle builder backed by SelectionModel.inspector, keeping their menu
checkmarks, selected sidebar rows and inspector in sync without separate menu state.

Map-focused Escape first uses MapRuler's existing cancellation behavior. With the ruler off it
uses the same selection callback as an empty-map click. SelectionModel alone decides which
global rows and in-game map overlays remain. The shared map callback announces an actual row
deselection through Apple's accessibility API; other focus contexts keep their own Escape.

All of the app's code is presentation; world-format rules live in ChunkseeKit.
EquipmentPresentation orders all filled saved slots, including unfamiliar player slots; a mob's
saved equipment, appearance and collar do not require an owner. WorldDetails keeps every readable
in-game map. DimensionPresentation routes records with missing or unavailable dimensions to the
first dimension's sidebar, while navigation remains available only for known destinations.
Blank maps use the map symbol and explain their empty picture. An unresolved saved dimension value
and its readable picture remain in the map inspector even when the picture cannot be overlaid.
ItemAppearance uses one filled tree for plant items across every item surface; BiomeGroup keeps
its leaf, following Ryan’s 2026-10-20 choice to distinguish those concepts. Shared symbols do not
need globally unique strings when their meaning is clear in context.

TradeText owns each complete villager offer for both the inspector and search results, including
the received item, both possible costs, enchantments and the saved sold-out status. Matching still
uses the separate searchable item names and identifiers, without presentation wording.
StructureGroup and PlaceGroup own the symbols shared by their sidebar rows and map markers.
StructureGroup.Catalog reads family membership from the world's shared structure-tag snapshot:
village, ocean_ruin, ruined_portal, shipwreck, mineshaft and abandoned_camp. A saved member of
overlapping tags uses the existing group order, then the exact untagged design groups. Readable
tags, including empty or replaced tags, are authoritative. If a family's tag is unavailable,
the former vanilla prefix rules preserve that family's no-game-files presentation; data-pack
tags still apply independently. Unmatched structures remain visible under Other Structures.
WorldDefinitions owns the catalog and immutable readers carry it into cached region projections.
Pack or selected-game changes replace those projections through the existing definition refresh;
the region facts cache and terrain tiles do not contain these presentation groups.
LayerVisibility records explicit structure-group visibility, giving groups missing from an older
settings schema their defaults. The legacy shown-only list migrates using its fixed historical
group schema, preserving previous choices while making the new Abandoned Camps group visible.
Strongholds use a door rather than a visibility eye, Trial Chambers use stacked rooms rather
than the Slime Chunks grid. Other Places use the native more symbol for uncategorized block entities.
Find Player Names uses a settings gear because it opens Settings. Storage uses an archive box,
Unopened Loot a gift and Buried Treasure a shipping box, following Ryan's 2026-10-20 decision
to distinguish those categories. Time Spent uses a clock rather than the item flame. World Info
and the World rows use filled variants; native shapes without one keep their own symbol.
Ryan's requested Zoom magnifier remains.
ChunkseeIndex.StoredItemTotal owns storage quantities and outer-container counts, including nested
items. StoredItem projects its results into app display names and count/name order; it does not
repeat the aggregation. The app and isolated test host link both published products.

WorldDetails keeps game rules by saved ID and derives sorted display rows. Wandering-trader
status uses Kit’s GameRule lookup; readable or translated labels never decide whether a rule
disables spawning. Rows use saved IDs so equal readable names remain distinct.

`DimensionPresentation.NameStyle` owns world-aware dimension labels, derived from the live catalog
for native Text and the `dimensionName` string adapter used by window titles and other consumers.
It carries the locale and dimension IDs without retaining the document or introducing another catalog owner.
Colliding readable labels include their full IDs; unique labels stay
concise. This also disambiguates different paths within a namespace and unavailable locations.
`ReadableName` owns identifier-to-word formatting for structures and custom dimension labels as
well as items. Identifier syntax and default namespaces come from ChunkseeKit's `Identifier`;
the app only formats its path or retains an unfamiliar value as readable fallback text. Vanilla
structure/place groups and block-color lookup require the Minecraft namespace, leaving custom
IDs distinct. The RegionFacts cache and tile-renderer version 8 discard classifications and pixels
made before this adoption. Structures retain their variant word order; the three vanilla dimension labels
remain localized. Window titles and native tab labels use the same dimension name, with the world name as the
subtitle. Names do not replace identifiers or document URLs.
DimensionPresentation.mapTitle supplies the map's accessibility label and image-sharing preview
with the same localized dimension-and-world title. Both callers pass their SwiftUI locale; custom
dimension collisions still use NameStyle, and saved world names remain literal.

RegionTileRenderer uses Chunk.forEachColumnRun for normal surface, cutaway and roof scans.
Kit owns WORLD_SURFACE/actual-block starts, checked heights and the section/column traversal;
the app resolves each reached palette entry once for color and accumulates contiguous water
depth during that same walk. Uniform sections arrive as spans, and columns stop independently.
Empty or unreadable surface columns remain unavailable; MOTION_BLOCKING no longer hides plants
above solid ground. Transparent display blocks, water shading and roof-view policy remain in the
app; map pixels and hover names use the same scan.
Normal-view shallow water blends the immediately underlying visible block's colour into the
existing water shade, fading the floor out by sixteen blocks. The same traversal retains that
colour; no extra block read or scan is added. Gaps, air and unreadable references leave the floor
unknown. The contiguous-water depth cap, surface location, hover/copy and Height/Water Depth
styles stay unchanged. Tile renderer version 12 discards the earlier opaque-water pixels.
WorldDetails owns one WorldDefinitions snapshot, loaded off-main through Kit with the selected
jar and the world's enabled packs. Opening first uses available world-pack facts; the shared game
request adds installed resources. Each resource category remains independently available. A failed
player refresh retains the previous coherent definitions/player snapshot until the next save. Initial player reads, later player reads and region scans use
its same enchantment dictionary. It also supplies dimension settings, possible biome associations,
trading definitions and the shared NotableBlock.Catalog. Current health and other saved facts stay
available when maximum health cannot be established.

MapSurfaceContext derives normal-view choices from resolved type/generation facts: known build
height reaches the shared heightmap reader; a known ceiling with nonempty generation bounds uses
the surface-rule range's upper plane for roof hiding and middle plane for biome sampling. Unknown
context keeps the actual surface, without a dimension-name ceiling fallback. Explicit cutaways
keep their chosen Y. Source/pack replacement updates each map's height scale and renderer context,
cancels obsolete renders/coordinate reads, and replaces the world's immutable region readers.
Their scan options include the enchantments and tag-derived block IDs; each shared index uses the
same catalog. Old index passes cannot publish into the replacement generation. Heat maps rebind to
the new reader, and retired readers/loaders drain under the world's BackgroundWork owner.
Tile renderer version 27 invalidates the previous interpretation. Source/color and surface keys
continue to distinguish their own inputs; the published Kit's RegionFacts version 20 invalidates
older scan envelopes.

`DocumentGroup` owns opening, recent documents, windows, tabs and restoration. A world folder
chosen in the Open panel or Open Recent is read as a world: the reader remembers it, and its window
opens the dimension folders with SwiftUI's `openDocument` and then closes itself. Navigate ▸
Dimension and cross-dimension jumps also use `openDocument`, which brings an already-open dimension
to the front; a jump runs once that dimension's view exists, and is dropped if it fails to open.
The opening action captures only `openDocument`, so a view never keeps its own document alive.
Native window and tab titles use `DimensionPresentation.dimensionName(_:)`, the same localized,
collision-safe name as the menus. URL-based DocumentGroup in macOS 27 retains folder titles
with navigationTitle at the document root, split-view root or map detail (verified in Release).
The small DocumentWindowTitle view sets only NSDocument.displayName through its existing
window controller; SwiftUI still owns the document, URL, window and native tabs. A view-scoped
observation reapplies the model’s display name if native restoration resets it; moving or closing
the view ends that observation. The adapter never edits a file URL or document contents.
The subtitle names the world; document URLs and native Open Recent remain tied to their folders.
Each dimension's map position is remembered in the world's `WorldSettings`.
WorldView owns the transient Go to Coordinates sheet flag. Navigate's command uses the focused
scene binding, while the sheet keeps its existing native controls and calls MapNavigation.
Other map commands remain disabled under the coordinate or saved-place sheets. WorldDocument's

## Interface wording

Use a consistent style for each UI role, following Apple's [Writing](https://developer.apple.com/design/human-interface-guidelines/writing)
and [Offering help](https://developer.apple.com/design/human-interface-guidelines/offering-help) guidance:

- Named features, headings, commands and inspector field labels use title case. A control's
  accessibility name identifies the same feature or action; a changing state belongs in its
  accessibility value. Descriptive numeric fields use sentence case, such as Zoom percentage
  and X coordinate.
- Activity/status text and explanatory checkbox labels use sentence case. Complete informative
  sentences end with punctuation; short status fragments do not. Ongoing activity ends with an
  ellipsis. Brief tooltips use sentence case without ending punctuation. Accessibility names
  also omit ending punctuation. Accessibility hints are brief phrases that begin with a capital
  letter and end with a period, following Apple's archived [hint guidance](https://developer.apple.com/library/archive/documentation/UserExperience/Conceptual/iPhoneAccessibility/Making_Application_Accessible/Making_Application_Accessible.html).
- Localize complete phrases and reuse the existing number, unit, duration and name owners.
  Keep contextual phrases such as Your inventory and Where you last died in sentence case.
  They identify whose data is shown; the inspector's Inventory or Last Death heading names the field.
- Preserve differences that carry information: Tamed By/Linked Pets and Riding With/On Shoulders
  describe opposite relationships; Location, World Spawn, Last Death, Respawn Point and map Center
  identify different locations. Boolean On/Off describes an enabled setting; Modded Yes/No,
  Cheats Allowed and a pet's sitting order describe different facts. Do not invent missing data
  to make labels match. Dimension names always come from DimensionPresentation, including in prose.
