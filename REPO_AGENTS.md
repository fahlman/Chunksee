# Chunksee — Repository Instructions

Read with the shared `AGENTS.md`.

## Read, interpret, display

Ryan's rules, approved 2026-10-25:

- The code knows formats, not content. What exists (blocks, items, mobs, biomes, structures,
  versions) comes at runtime from the save, the installed Minecraft, the world's data packs
  and the language files.
- **WWMD — What Would Minecraft Do?** Do what Minecraft does, unless Ryan explicitly
  chooses otherwise.
- **Lists are for exceptions,** and exceptions are facts in the game's code that the data
  doesn't tell us. Each entry names its code source. Anything the data could supply is a defect.
- Code-only facts are regenerated by a tool at each release. They are never hand-typed and
  never kept per snapshot.
- **Show what we can.** Never hide saved data because it's unfamiliar. "Unknown" is only for
  the facts the data can't tell us.
- **No version numbers in code or UI text.** Data readers read any version whose files parse.
- **Be useful, not a pain.** Notices inform and never block.
- **No self-made maintenance.** A new Minecraft version should need no code change, or at
  most one tool run.

Chunksee presents facts supplied by ChunkseeKit and ChunkseeIndex. It does not decode game
files or keep another copy of game rules. Read the user's installed language files through Kit;
reading those files at runtime is not redistribution. Choose the user's language in the app,
with the game's English name and then a readable ID as fallbacks.

Existing implementation notes below describe the current code and its evidence; they are not
exceptions to these rules. The migration is coordinated in
[fahlman/ChunkseeKit#222](https://github.com/fahlman/ChunkseeKit/issues/222):
Kit's readers and generated code facts come first, then their published API is adopted here.
Names and naming exceptions are tracked on #438 and fahlman/ChunkseeKit#225; hidden saved facts
on #439 and fahlman/ChunkseeKit#229/#235; structure membership on #435 and
fahlman/ChunkseeKit#233; biome lists and colors on #436 and fahlman/ChunkseeKit#223; missing
pictures on #430/#433 and fahlman/ChunkseeKit#234/#236; and dynamic version notices on #434
and fahlman/ChunkseeKit#237. #431 retains the separately held snapshot preparation.
Map palettes, marker colors and SF Symbols are presentation choices; they must not decide what
exists or hide saved data. Existing cave-biome inference remains subject to Ryan's hold on
fahlman/ChunkseeKit#130.

## Project

Chunksee is a Mac app for viewing Minecraft: Java Edition worlds. Ryan approved it on 2026-10-09.
It was called MCWorld until 2026-10-10, when it and its engine (MCWorldKit, now ChunkseeKit) were
renamed (fahlman/Chunksee#75); earlier issues, PRs and commits use the old names.

- **First scope:** open a world and show a top-down view of it.
- **Later:** overlays for strongholds, villages and other structures. These aren't approved for
  work yet.
- **Dependency direction:** **Chunksee app → ChunkseeKit and ChunkseeIndex**. ChunkseeKit is the
  open-source engine that reads world files (fahlman/ChunkseeKit); the same package's ChunkseeIndex
  product owns shared aggregation. This app owns presentation. World-format rules belong in
  ChunkseeKit and are never re-implemented here.

### Layers

Each layer depends only on layers above it in this list, through their public interfaces.

1. **Kit** (ChunkseeKit, ChunkseeIndex) reads saves and game files and owns every format rule and
   code-only game fact.
   - **One normalized chunk:** each save's layout, data-version renames and block entities are
     normalized and upgraded once per read, and readers reuse that result.
     - Independent facts stay readable when another part fails: containers, signs, spawners,
       creatures and inhabited time still read when the terrain is malformed or unsupported.
     - Selective reads and skipping keep working, raw-NBT APIs are unchanged, and nothing retains
       a whole world eagerly.
   - **Fields read the game's way:** each field declares the game codec that reads it (for example
     widening integer reads versus Java's narrowing conversion) and uses the shared implementation
     of that codec, including its missing and invalid behavior. An accessor is changed only on
     evidence from that field's game reader, never by a global replacement.
   - **Published versions:** Kit publishes an interpretation version for each kind of fact the app
     caches: terrain and surface, light, assets and region facts. Each is owned beside its code.
     The release tool adds a digest of the generated facts each one uses, so a tool run that changes
     a covered fact changes the version.
   - **Saved inputs, derived results:** where a fact combines saved data with data-pack or game-file
     definitions (maximum health with enchantments, for example), the cache keeps the typed saved
     inputs and Kit's resolver works out the result with the current definitions. A definition
     change then needs no region reread. Parameterized scans may still cache their output under
     their complete option identity.
2. **Game files** (`MinecraftResources`, `GameDataLibrary` and `GameArtworkLibrary`, #466). One
   owner chooses the Minecraft folder and decides whether artwork is used.
   - **Always available:** game data, meaning definitions, tags, model geometry, lighting rules,
     numeric biome data and the game's language files.
   - **Only with Use Game Artwork on:** the artwork capability (textures, colormaps and pictures).
     Nothing else decides that policy.
3. **World snapshot** (`WorldResources`). Each open world has one observable snapshot of what its
   windows show:
   - definitions, lighting, night lighting and biome colors;
   - players and player records;
   - World Info facts (game rules, weather, time, the dragon fight, the wandering trader) and
     in-game maps;
   - version notices, names and search results.

   How each part loads and publishes:
   - **One loader:** each part comes from one shared loader type with declared inputs: the world's
     file changes plus the game-data and artwork identities. It isn't a second task registry;
     `BackgroundWork` keeps owning lifetimes.
   - **Two refresh contracts, both owned by the loader:**
     - *Same-source changes,* such as a world save, coalesce. A running pass finishes and
       publishes its progress, and changes arriving meanwhile are merged into the next pass instead
       of restarting it: changed regions are unioned, and a complete refresh dominates subsets.
       Producers that build incrementally, such as the region index and slime chunks, keep their own
       merge rules and read only what is missing.
     - *Source replacement* rejects every result from the old source and cancels its work where
       appropriate. That covers a new game-data or artwork identity, new region readers and
       definitions, and a document reread or Finder move.
   - **Failure, empty and removal differ:** a transient read failure keeps the last coherent value
     from the same source. A successful empty result clears removed facts. Removing or replacing
     the source keeps nothing incompatible. Refreshing the same player keeps their records;
     selecting another clears them.
   - **Independent where independent:** independent parts publish on their own; game data doesn't
     wait for biome colors. Only related values publish together, such as definitions with the
     players that depend on them, or the index with its player projection.
   - **Views observe:** sessions and views read the snapshot; nothing pushes values into maps by
     hand. No refresh depends on a visible view receiving a change.
   - **Per-window requests stay per window:** the world owns keyed shared results, never one global
     selected player or active query.
     - Two windows can show different players' records, and switching one doesn't clear the other.
     - Editing one window's query doesn't restart unrelated saved queries, and closing one waiter
       doesn't cancel work another still needs.
     - Search keeps its coherent-publication guard.
   - **One world, one snapshot:** open worlds are registered under the world folder's persistent
     identity, not its path, so each world has exactly one snapshot.
   - **Names:** one naming service answers "what is this called" for every kind: items, blocks,
     mobs, biomes, effects, enchantments with levels, professions, dimensions and structures. It
     holds the fallbacks and exceptions inside it.
     - Views and search both use it.
     - Markers and search hits carry IDs, not finished strings.
     - Names come from the game data and the Mac's language, so they stay available with artwork
       off.
4. **Map presentation** (`MapModel`). Each dimension's map has one presentation value: style, depth,
   block filter, lighting mode, shadows, biome blending and overlays.
   - **Chosen, not shown:** it records what the user chose and is saved as one per-dimension record.
     What can be shown now (Height only with a known height scale, for example) is derived from that
     choice plus availability and never written back.
   - **Styles declare what they use:** each style states which inputs it uses (material colors,
     lighting, shadows and close-up detail), so that rule is decided once.
   - **One drawing input:** one value derived from the presentation and the snapshot feeds the
     screen, Copy/Share and area export.
     - It holds drawing facts only, not routing, selection or permissions.
     - Copy keeps using the tiles already visible, and area export keeps streaming its area with
       bounded memory.
5. **Windows, menus and views** show the snapshot and the presentation, and send user input to the
   owner of each setting. They don't parse game files, start hidden reads while drawing, build
   cache keys or decide rules. Each window has:
   - one selection value, the existing identity resolved through `SelectionModel`'s private
     transition, with the kept in-game-map overlay preserved;
   - one inspector-visibility value, so showing the inspector again keeps the selected row;
   - one highlighted set *derived* from the selection, which the map compares against and nobody
     edits separately;
   - one sheet value, so "a sheet is open" can't miss a sheet (#474).

### Caches

The caches are `TileCache`, `ScanCache`, the in-memory tiles and the in-game map image cache. Each
belongs to the code that produces its output.

- **Typed keys:** each cache key is built from typed values of every input that changes its output.
  That includes Kit's interpretation versions, the game-data and artwork identities, and the
  presentation values the output depends on. Whole Kit values are used, never hand-copied fields.
- **Stable identities:** persisted identities are stable across launches, never runtime UUIDs or
  Swift's randomized hash values. Catalog identities are computed once, when an immutable
  publication is made, not per request.
- **The app's version covers only the app:** no hand-maintained counter stands in for a Kit or
  game-file input; the app's renderer version covers only its own drawing code.
- **Tests prove both directions.** A change that affects output (decoder, definitions, style)
  rejects old entries. An unchanged reopen reuses them. The artwork setting doesn't rescan saved
  facts. Lighting that doesn't change cached unlit pixels doesn't invalidate them.
  - **Fixed-output tests** in Kit (decoded facts) and the app (pixels) catch changed output for
    their fixtures. They can't catch an unexercised case, so review of the version contract stays
    required.
- **In-memory entries carry their key,** and an entry whose key no longer matches is dropped.

### Rules for every change

- A setting, policy or mode has one owner, and its consumers receive the result, not a flag to
  check. A cross-cutting rule left to convention, a flag or default argument that silently picks
  the unsafe choice, or two handles told apart only by name is a required review finding.
- There is one copy of the latest-result rule, of each setting's default, and of each style's
  inputs.
- A step that moves a rule to its owner deletes the code it replaces in the same PR.
- **Kept as they are, not revalidated:** document opening and bookmarks, preference migration,
  online-name consent, and memory and export budgets. A step that touches them proves it preserves
  them.

## Modules

VisibilityCommand owns the shared Show/Hide label, binding and action. Compact eye buttons show
the current state; context-menu symbols show the action (crossed eye for Hide, open eye for Show).

WorldCommands routes native commands through the focused document. Edit > Find keeps Find and
Save Search together; Shift-Command-F saves a nonempty, unsaved query through SearchModel. View's
Command-9 Fit World uses MapNavigation's existing fit/availability calculation. World Info and
Storage share one native toggle builder backed by SelectionModel.inspector, keeping their menu
checkmarks, selected sidebar rows and inspector in sync without separate menu state.

Map-focused Escape first uses MapRuler's existing cancellation behavior. With the ruler off it
uses the same selection callback as an empty-map click. SelectionModel alone decides which
global rows and in-game map overlays remain. The shared map callback announces an actual row
deselection through Apple's accessibility API; other focus contexts keep their own Escape.

All of the app's code is presentation; world-format rules live in ChunkseeKit.
WorldResources derives the saved version from its current WorldInfoSnapshot and owns the comparison
with its selected game library.
WorldVersionNotice compares the supplied data versions and displays their supplied names; absent
saved data versions do not produce a newer-world notice. A successful metadata refresh updates
the saved version, and source-generation checks reject retired game files. The non-blocking map
banner is remembered once per version pair in WorldSettings, shared across dimension documents;
World Info keeps the notice while the comparison applies. Neither presentation gates any reads.
The comparison uses the game-data reader, so turning artwork off does not hide it.
Notice text accepts the column's proposed height: forcing its ideal vertical size inflates
the native split view's minimum height during layout. Window tests check the actual split-view
and notice bounds through source changes, resizing, inspector visibility and dismissal.

EquipmentPresentation orders all filled saved slots, including unfamiliar player slots; a mob's
saved equipment, appearance and collar do not require an owner. WorldDetails keeps every readable
in-game map. DimensionPresentation routes records with missing or unavailable dimensions to the
first dimension's sidebar, while navigation remains available only for known destinations.
Blank maps use the map symbol and explain their empty picture. An unresolved saved dimension value
and its readable picture remain in the map inspector even when the picture cannot be overlaid.
ItemAppearance uses one filled tree for plant items across every item surface; BiomeGroup keeps
its leaf, following Ryan’s 2026-10-20 choice to distinguish those concepts. Shared symbols do not
need globally unique strings when their meaning is clear in context.

GameNames.tradeOffer owns each complete villager offer for both the inspector and search results, including
the received item, both possible costs, enchantments and the saved sold-out status. Matching still
uses the separate searchable item names and identifiers, without presentation wording.
StructureGroup and PlaceGroup own the symbols shared by their sidebar rows and map markers.
StructureGroup.Catalog reads family membership from the world's shared structure-tag snapshot:
village, ocean_ruin, ruined_portal, shipwreck, mineshaft and abandoned_camp. A saved member of
overlapping tags uses the existing group order, then the exact untagged design groups. Readable
tags, including empty or replaced tags, are authoritative. If a family's tag is unavailable,
the former vanilla prefix rules preserve that family's no-game-files presentation; data-pack
tags still apply independently. Unmatched structures remain visible under Other Structures.
WorldDefinitions owns the catalog and immutable readers carry it into cached region projections.
Pack or selected-game changes replace those projections through the existing definition refresh;
the region facts cache and terrain tiles do not contain these presentation groups.
LayerVisibility records explicit structure-group visibility, giving groups missing from an older
settings schema their defaults. The legacy shown-only list migrates using its fixed historical
group schema, preserving previous choices while making the new Abandoned Camps group visible.
Strongholds use a door rather than a visibility eye, Trial Chambers use stacked rooms rather
than the Slime Chunks grid. Other Places use the native more symbol for uncategorized block entities.
Find Player Names uses a settings gear because it opens Settings. Storage uses an archive box,
Unopened Loot a gift and Buried Treasure a shipping box, following Ryan's 2026-10-20 decision
to distinguish those categories. Time Spent uses a clock rather than the item flame. World Info
and the World rows use filled variants; native shapes without one keep their own symbol.
Ryan's requested Zoom magnifier remains.
ChunkseeIndex.StoredItemTotal owns storage quantities and outer-container counts, including nested
items. DimensionContent keeps those raw totals; GameNames.storedItems projects them into current
display names and count/name order without repeating aggregation. A language change needs no index
reread merely to rename Storage rows. The app and isolated test host link both published products.

WorldDetails keeps game rules by saved ID and derives sorted display rows. Wandering-trader
status uses Kit’s GameRule lookup; readable or translated labels never decide whether a rule
disables spawning. Rows use saved IDs so equal readable names remain distinct.

`GameNames.DimensionStyle` owns world-aware dimension labels and map-title phrasing.
DimensionPresentation supplies the live catalog to the world's GameNames service through
`dimensionStyle(for:)`, for native Text and the `dimensionName` string adapter used by window titles
and other consumers. The immutable style carries the locale and dimension IDs without retaining
the document or introducing another catalog owner; captured styles retain their catalog context.
Colliding readable labels include their full IDs; unique labels stay
concise. This also disambiguates different paths within a namespace and unavailable locations.
`ReadableName` supplies identifier-to-word formatting to GameNames for structures and custom dimension
labels as well as items. Identifier syntax and default namespaces come from ChunkseeKit's `Identifier`;
the app only formats its path or retains an unfamiliar value as readable fallback text. Vanilla
structure/place groups and block-color lookup require the Minecraft namespace, leaving custom
IDs distinct. The RegionFacts cache and tile-renderer version 8 discard classifications and pixels
made before this adoption. Structures retain their variant word order; the three vanilla dimension labels
remain localized. Window titles and native tab labels use the same dimension name, with the world name as the
subtitle. Names do not replace identifiers or document URLs.
DimensionPresentation.mapTitle supplies the world name to that same style for the map's accessibility
label and image-sharing preview. Both callers pass their SwiftUI locale; custom dimension collisions
still use GameNames.DimensionStyle, and saved world names remain literal.

RegionTileRenderer uses Chunk.forEachColumnRun for normal surface, cutaway and roof scans.
Kit owns WORLD_SURFACE/actual-block starts, checked heights and the section/column traversal;
the app resolves each reached palette entry once for color and accumulates contiguous water
depth during that same walk. Uniform sections arrive as spans, and columns stop independently.
Empty or unreadable surface columns remain unavailable; MOTION_BLOCKING no longer hides plants
above solid ground. Transparent display blocks, water shading and roof-view policy remain in the
app; map pixels and hover names use the same scan.
Normal-view shallow water blends the immediately underlying visible block's colour into the
existing water shade, fading the floor out by sixteen blocks. With available game artwork,
GameArtworkLibrary reads the first water-texture frame's average opacity once per library. That
opacity limits the visible floor, whose brightness uses the same existing depth shade. Missing
water artwork preserves the former blend exactly. The same traversal retains the floor colour;
no extra block read or scan is added. Gaps, air and unreadable references leave the floor unknown.
WorldDefinitions supplies the composed water-fluid tag. MapSurfaceContext carries it to the
shared surface/depth/hover scan, where Kit's saved-state fluid and upper-face facts choose water

## Interface wording

Use a consistent style for each UI role, following Apple's [Writing](https://developer.apple.com/design/human-interface-guidelines/writing)
and [Offering help](https://developer.apple.com/design/human-interface-guidelines/offering-help) guidance:

- Named features, headings, commands and inspector field labels use title case. A control's
  accessibility name identifies the same feature or action; a changing state belongs in its
  accessibility value. Descriptive numeric fields use sentence case, such as Zoom percentage
  and X coordinate.
- Activity/status text and explanatory checkbox labels use sentence case. Complete informative
  sentences end with punctuation; short status fragments do not. Ongoing activity ends with an
  ellipsis. Brief tooltips use sentence case without ending punctuation. Accessibility names
  also omit ending punctuation. Accessibility hints are brief phrases that begin with a capital
  letter and end with a period, following Apple's archived [hint guidance](https://developer.apple.com/library/archive/documentation/UserExperience/Conceptual/iPhoneAccessibility/Making_Application_Accessible/Making_Application_Accessible.html).
- Localize complete phrases and reuse the existing number, unit, duration and name owners.
  Keep contextual phrases such as Your inventory and Where you last died in sentence case.
  They identify whose data is shown; the inspector's Inventory or Last Death heading names the field.
- Preserve differences that carry information: Tamed By/Linked Pets and Riding With/On Shoulders
  describe opposite relationships; Location, World Spawn, Last Death, Respawn Point and map Center
  identify different locations. Boolean On/Off describes an enabled setting; Modded Yes/No,
  Cheats Allowed and a pet's sitting order describe different facts. Do not invent missing data
  to make labels match. Dimension names use GameNames with DimensionPresentation's live catalog
  context, including in prose.
